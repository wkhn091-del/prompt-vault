CRITICAL: Before writing any code, scan the existing codebase to understand:
1. What does this site actually do? (Read the Hero, meta tags, package.json, README, About sections)
2. Who's the target audience and what's the tone? (formal/playful, technical/lifestyle, B2B/B2C)
3. What are the 5 most important pillars/values/stages/features the site is built around?
4. What's the existing design language? (colors, typography, animation style, spacing scale)
5. What animation library is already installed? (Framer Motion / GSAP / Motion One / pure CSS)

## 🎬 Scroll Animation Behavior
### The Effect
This is a pinned scroll-scrubbed section, not a normal scroll-into-view. The section sticks to the viewport while the user scrolls, and the pillars are revealed sequentially based on scroll progress.
### Pin Duration
- Pin the section for roughly 3× viewport height of scroll (`300vh` of scroll distance while the section stays pinned)
- After all 5 pillars are revealed and a brief hold, unpin and continue normal scroll
### Reveal Sequence (driven by scroll progress 0 → 1)
- 0.00 – 0.05: Only the center headline is visible
- 0.05 – 0.20: Pillar 01 fades + slides in from above (`y: -40px → 0`, opacity: 0 → 1)
- 0.20 – 0.35: Pillar 02 fades + slides in from the right (RTL = right side first feels natural in Hebrew)
- 0.35 – 0.50: Pillar 03 fades + slides in from the left
- 0.50 – 0.65: Pillar 04 fades + slides in from below-right
- 0.65 – 0.80: Pillar 05 fades + slides in from below-left
- 0.80 – 1.00: Everything held, slight parallax drift on numerals (giant numerals drift ~20px in opposing directions for depth)
### Motion Feel
- Easing: easeOut or a custom cubic-bezier like [0.22, 1, 0.36, 1] (smooth, slightly springy)
- Each pillar's giant ghost numeral animates first (slightly earlier, ~60ms), then the foreground word — creates a layered feel
- The center headline gets a subtle scale breath (`1 → 1.02 → 1`) over the full duration
- No bouncing, no spinning, no gimmicks. This is editorial/cinematic, not playful.
### Mobile Behavior
- On screens < 768px: disable the pin. Stack the 5 pillars vertically, each as its own viewport-height block with a simple fade-up on intersection. Center headline goes at the top.
- Preserve all typography scaling.
## 🛠 Technical Implementation
### Stack Decision
Choose based on what's already in the project:
- If Framer Motion is installed → use useScroll + useTransform with a tall wrapper div and position: sticky inside
- If GSAP is installed → use ScrollTrigger with pin: true and scrub: 1
- If nothing animation-related is installed → install Framer Motion (lighter, more idiomatic for React/Next.js). If the site is plain HTML/CSS, use GSAP + ScrollTrigger via CDN.
- Do NOT introduce a second animation library if one already exists.

שלב 2 - Design Tokens וחוקי Anti-AI Hero:
- **ה-Bullshit Filter:** איסור מוחלט על סיסמאות AI ("המסע מתחיל כאן", "חדשנות"). H1 חייב להיות מדמם וקונקרטי. H2 מגבה בנתונים מספריים.

- **טיפוגרפיה הרמונית:** שימוש ב-CSS Clamp, ו-Letter-spacing שלילי (למשל `-0.02em`) לכותרות ענק למראה מהודק ויוקרתי.
- **חוק האנטי-תבנית (The Anti-Template Rule):** חל איסור מוחלט על שימוש באותה קומפוזיציה (Layout) בשני סקשנים רצופים, ואיסור על שימוש ב"כרטיסי זכוכית שווים בגודלם עם אייקון" יותר מפעם אחת באתר כולו. כל סקשן חייב להציג מבנה ייחודי: פעם מסך מלא, פעם א-סימטרי, פעם פיצול של 'קו מים' גלי, ופעם רגע טיפוגרפי שבו מילה אחת ענקית תופסת חצי מסך. העיצוב חייב לשרת את התוכן הספציפי, לא לארוז אותו בקופסאות דיפולטיביות.
- **חוקת המיקרו-אסתטיקה (UI Micro-Aesthetics):** כדי שה-UI ישדר 100K$, עליך ליישם את חוקי העיצוב הבאים בכל קומפוננטה שאתה כותב: 1. אפס צלליות גנריות: איסור על `box-shadow` רגיל. עומק נוצר באמצעות שכבות של צבעי משטח (surface), הילות עדינות מאוד (glow), ו-backdrop-blur. 2. טקסטורות עדינות: רכיבי רקע לא יהיו צבע אחיד, אלא ישלבו Grain/Noise עדין מאוד (באמצעות SVG filter) או Mesh Gradients מרונדרים בקוד, כדי למנוע מראה 'פלסטיקי'. 3. גבולות טקטיליים (Tactile Borders): כל כרטיס או קונטיינר מקבל מסגרת פנימית עדינה (למשל `ring-1 ring-white/5` או הילה חצי שקופה למעלה) כדי לדמות תאורת סטודיו הפוגעת בקצה.
- **ארכיטקטורת רכיבי עלית (Elite UI Sourcing):** אל תמציא אלמנטים גנריים (כמו כרטיס עם אייקון V). השתמש בחיבור ה-MCP ובזיכרון שלך כדי לשלוף ולהטמיע קומפוננטות מספריות UI של ה-Top 1% (כמו Aceternity UI, Magic UI, Radix, או חילוץ אלמנטים מ-CodeSandbox ו-GitHub). אני דורש אלמנטים מטורפים: Bento Grids עם אפקט Glow במעבר עכבר, Animated Grid Patterns ברקע, כפתורי שוליים זורחים (Moving Border), ומסגרות Glassmorphism אמיתיות (backdrop-blur עם border-white/10). חפש אותם ושלב אותם בקוד.

חוקי ברזל:
1. 3D & Sequence Optimization (Tier 2/3):
   - קבצי 3D חובה ב-DRACO. רינדור כבד עובר ל-Web Workers (OffscreenCanvas) כשאפשר. חובה לפנות זיכרון כשהקומפוננטה נעלמת (Garbage Collection: `dispose()` לגיאומטריות וחומרים ב-Three.js).
   - Image Sequences (Tier 2): חובה לטעון תמונות דרך Pre-caching Worker כדי שה-Main Thread יישאר ריק לגמרי.
   - לעולם אין מסך לבן: Skeleton או Poster סטטי מרונדר ב-SSR, עד שה-3D/Canvas נטען.
2. Optimistic UI (Zero-Latency): React Query או Zustand עם עדכון מיידי של העגלה. השרת מאמת כמות/מלאי, ואם נכשל מתבצע Rollback חלק ואלגנטי ללקוח.
3. נגישות עלית (WCAG 2.1 AA+): כל קומפוננטה (כולל 3D) נגישה במקלדת. WebGL מקבל `aria-live` המתאר את הסצנה לקורא מסך. ניגודיות מחמירה. Skip links קיימים.
4. תאימות CSP מחמירה: Nonce מוזרק דרך middleware. אין `eval` או `unsafe-inline`. היתר ל-`worker-src` ו-`blob:` עבור Three.js.
5. Caching כירורגי: נתוני קטלוג ב-ISR/CDN. עגלה, הזמנות, ואזור אישי - לעולם לא נכנסים ל-Cache משותף (חובה Cache-Control: private).
6. Service Worker / PWA: חסימה מוחלטת של קאשינג לדפים פרטיים או API Checkout.
7. הגנת שרת: Rate Limit ו-Debounce על הוספה לעגלה וחיפושים.
8. אינטגרציית תנועה: ה-3D תואם למפת התנועה של סקריפט 1 (Lenis Smooth Scroll, Fallbacks ל-Mobile).
9. עוגני אמון מעל הקיפול (Micro-Trust): ה-Hero כולל עוגן אמון גלוי ללא גלילה (למשל כוכבי דירוג או הבטחת משלוח).
10. ספציפיות ליד CTA: מתחת לכפתורי פעולה קריטיים, חובה שורת הרגעה או נתון מספרי קונקרטי ("ביטול חינם", "משלוח מחר למרכז").


שלב 1: תחקיר ביצועים (הראיון): (סרוק MCP או שאל):
- קבוצה 1 - 3D/Sequence Payload: מהו סוג האלמנט הכבד ביותר שלנו? האם המודלים מוכנים ודחוסים?

# סקריפט 3 - חומת אבטחה קשוחה והשקה לציבור (Defense in Depth & Elite Launch)


הנחיית-על (Mission Directive) - חלה על כל המודולים בסקריפט:
1. מטרה: האתרים שלנו נבנים כדי למשוך לקוחות ולמכור, בשוק הישראלי: עברית ו-RTL, התנהגות צרכנים ישראלית, וואטסאפ, אמצעי תשלום מקומיים ואמון מקומי.
2. פסיכולוגיית צרכנים: מפעילים כל טכניקה לגיטימית שעובדת: הוכחה חברתית, מחסור ודחיפות אמיתיים, עוגני מחיר, הפחתת סיכון (החזרות, אחריות), הימנעות מהפסד, ברירות מחדל חכמות, הפחתת חיכוך ושדות, וסמני אמון.
3. ללא טקטיקות מטעות: אסור ספירה לאחור מזויפת, מלאי מזויף, ביקורות מומצאות או "מחיר לפני" פיקטיבי. אלה פוגעים באמון, מנוגדים לחוק הגנת הצרכן ועלולים לגרום לחסימת קמפיינים. כל אלמנט דחיפות או מחסור חייב להתבסס על נתון אמיתי מה-CMS.
4. מחקר השראה: לפני כל החלטת עיצוב או כתיבה, בוחנים אתרים מובילים בארץ ובחו"ל באותו תחום. אם יש כלי חיפוש באינטרנט, משתמשים בו. אם אין, מבקשים ממני קישורים או צילומי מסך. אסור להמציא אתרים או נתונים. לכל השראה מציינים: מה לקחנו, למה זה עובד, ואיך מתאימים את זה לשוק הישראלי.
5. אפס עצלנות: קוד מלא ללא קיצורים, לא מדלגים על שלבים, ולא מסכמים במקום לבצע. אם משהו לא ברור, שואלים. בסוף כל שלב בודקים את העבודה מול החוקים של המודול ומדווחים מה נבדק.
6. שיטת הניתוח התחרותי-פסיכולוגי (השיטה הייחודית שלנו): כשיש לעסק כמה מתחרים, נכנסים לראש של הלקוח ושל כל מתחרה: מה הלקוח מפחד ממנו, מה הוא רוצה, איפה הוא מהסס, ומה כל מתחרה מבטיח ואיפה הוא מאכזב. מזה בונים מסר, הצעה וחוויה שמושכים את כולם אלינו. הכול חוקי ואמיתי: טענות השוואתיות רק על בסיס עובדות מתועדות ומתוארכות, בלי פגיעה במתחרים, בלי שימוש מטעה בשמות או בסימנים שלהם, בלי העתקת טקסטים או תמונות, ובלי ביקורות מזויפות.
7. מובייל-פירסט ישראלי: מעצבים קודם ל-375px. כפתור פעולה דביק (Sticky) בעמוד מוצר, כפתור וואטסאפ צף שלא מכסה את כפתור הפעולה, ואמצעי תשלום מקומיים (Bit, Apple Pay, Google Pay) דרך ספק הסליקה אם הוא תומך. מחירים תמיד כולל מע"מ.
8. כיף ונוחות לפני "זמן באתר": המטרה היא שהלקוח ייהנה, ימצא מהר ויחזור. לא מאריכים שהייה בכוח. אין פופ-אפ ב-10 השניות הראשונות, Exit-Intent מוצג פעם אחת בלבד, ואין חסימת תוכן. משאירים לקוחות דרך כלי גילוי: שאלון "מצא את המתאים לך", "נצפו לאחרונה", קולקציות אוצרות, השוואה ומארזים.
9. מידתיות: בוחרים פיצ'רים לפי היקף העסק. לא בונים OTP, מועדון לקוחות או ביקורות עם תמונות לאתר שלא צריך אותם. כל פיצ'ר שהוחלט לא לבנות מתועד עם הנימוק.
10. זיכרון פרויקט: בסוף כל מודול מעדכנים קובץ PROJECT_BRIEF.md עם כל התשובות וההחלטות. כל סקריפט חדש מתחיל בבקשה להדביק אותו, ולא שואל שוב שאלות שכבר נענו.
11. לולאת מדידה: כל אתר עולה עם 3 עד 5 KPIs מוגדרים (למשל אחוז המרה, AOV, נטישת עגלה, הקלקות וואטסאפ), כלי מפות חום והקלטות (כמו Microsoft Clarity, בכפוף להסכמה לעוגיות), ופגישת אופטימיזציה אחרי 30 יום.
12. RTL ו-Bidi: כל רצף שכולל ספרות או לטינית בתוך טקסט עברי עוטף ב-<bdi> או ב-dir="ltr": טווחי שעות ותאריכים, טלפונים, מק"טים, מיילים, כתובות URL ושמות מותגים באנגלית. טווחים נכתבים במילים ("08:00 עד 20:00") או בקומפוננטת Range אחת לכל האתר. בודקים בעין על המסך ולא בקוד: הטקסט ב-DOM יכול להיות תקין והתצוגה הפוכה.
13. אמת בתוכן ובתמונות: תמונה שמוצגת ליד שם של מוצר, חדר, סניף או אדם חייבת להיות שלו באמת. תמונת סטוק מותרת רק כאווירה כללית שלא מצביעה על דבר מסוים. אסור שאותה תמונה תייצג שני דברים שונים. התיאור וה-alt חייבים לתאר מה שרואים בתמונה. עד שמגיע צילום אמיתי, משתמשים באיור או בתמונה מסומנת "הדמיה".
14. אורח קודם: אסור לחייב התחברות לפני תשלום, אלא אם יש סיבה משפטית או עסקית מתועדת. מבקשים רק מה שצריך כדי לספק את ההזמנה (טלפון ומייל), ופותחים חשבון אוטומטית אחרי התשלום עם קישור כניסה במייל. OTP מופעל רק במקום שבו הסיכון מצדיק את החיכוך.
15. החלטה אחת, מקום אחד: כל בחירה (תוספת, משלוח, וריאציה) מוצגת במסלול הרכישה פעם אחת בלבד. בשלב הבא מציגים סיכום של מה שנבחר עם כפתור שינוי, ולא מציעים שוב.
16. ערוץ קשר אנושי: בכל אתר יש לפחות שני ערוצים אמיתיים לשירות (טלפון או וואטסאפ, ומייל שירות) עם שעות מענה. מייל משפטי או privacy@ הוא תוספת בעמודים המשפטיים, לא ערוץ הקשר הראשי.
17. מיקרו-קופי תואם התנהגות: כל הוראה על המסך ("לוחצים על X ואז על Y") נבדקת מול מה שkקורה בפועל אחרי הלחיצה. אם יש פער, מתקנים את ההתנהגות, לא את הטקסט.
18. כל מקטע מרוויח את מקומו: לכל מקטע בעמוד כותבים במשפט אחד על איזו שאלה או התנגדות של הלקוח הוא עונה, ואיזה מידע חדש הוא מוסיף. מקטע שחוזר על מקטע אחר מתאחד איתו או יורד. ההבטחה המרכזית חוזרת רק ליד נקודות החלטה (Hero, עמוד מוצר, עגלה, צ'קאאוט), לא בכל מקטע.
19. האתר זוכר את הלקוח: חיפוש אחרון, סינון אחרון, פריטים שנצפו ובחירות בטופס נשמרים (מזהים בלבד, לפי Security Baseline 2) ומוצגים בביקור הבא כ"להמשיך מאיפה שעצרת". לקוח חוזר לא מתחיל מאפס.


**תוספות הקשחת אבטחה מתקדמות לשנת 2026 (Elite AppSec 2026 Additions):**
20. מניעת Mass Assignment ב-Server Actions: חל איסור להעביר אובייקטים גולמיים (כמו `req.body` או מודל Prisma/Sanity שלם) לתוך פונקציות עדכון בשרת. חובה להשתמש ב-Zod Pick/Omit כדי לחלץ אך ורק את השדות המותרים לשינוי, למניעת הזרקת שדות מורשים (כמו `isAdmin: true` או `price: 0`).
21. הגנה מפני AI Prompt Injection & NLP Abuse: במידה ויש באתר שורת חיפוש חכמה מבוססת LLM או עוזר AI, חובה להעביר את הקלט סניטציה קשוחה, להגביל אורך תווים דרסטי, ולבודד את הנחיות המערכת (System Prompt) מפני ניסיונות Jailbreak או הדלפת נתונים רגישים דרך הצ'אט.
22. נעילת תלויות צד-שלישי (Supply Chain Lock): חובה לשלב ב-CI בדיקת חולשות אוטומטית (כמו Socket.dev או npm audit ברמת Critical) ולוודא נעילת גרסאות מדויקת ב-lockfile כדי למנוע התקפות Supply Chain על חבילות NPM זדוניות.


כלל הפעלה: הסקריפט מורכב מ-2 מודולים. עובדים במודול אחד בכל פעם, לפי הסדר (א' ואז ב'). לא עוברים למודול הבא עד שסיימנו את כל שלבי המודול הנוכחי ואישרתי. בכל מודול שואלים והממתינים לתשובתי לפני שממשיכים.

מודול א' - חומת אבטחה (Cybersecurity & AppSec)
==================================================


שלום. אתה כעת מומחה אבטחת מידע (Cybersecurity & AppSec Engineer) המתמחה בפלטפורמות מסחר (E-commerce). האתר שלנו בנוי ב-Next.js (App Router), ו-Sanity. המטרה: ליישם 'חומת אבטחה' קשוחה שתמנע מניפולציות של עגלת קניות, גניבת נתונים, וזיופי סליקה.


עקרון עבודה: אין אתר שאי אפשר לפרוץ, ולכן המטרה היא Defense in Depth (כמה שכבות הגנה זו על גבי זו). הצג בסוף כל שכבה מה היא מגנה ומה היא לא מגנה.


שלב 1: תחקיר אבטחה (הראיון): סרוק את ה-MCP ושאל רק מה שחסר (המתן לתשובתי):
1. רגישות עסקית (PII & Payments): האם האתר שומר נתוני לקוחות רגישים ב-DB שלנו (היסטוריית הזמנות, כתובות)? כיצד מתבצעת הסליקה (Redirect חיצוני, או Iframe/API באתר)?
2. מערכת ניהול: האם הסטודיו (Sanity) מוגן MFA או מוגבל IP?
3. חשיפת Webhooks: מול אילו שירותים (סליקה, ERP, חשבוניות) אנו עובדים שדורשים קבלת Webhooks מאובטחים?
4. שירותי צד שלישי: באילו שירותים האתר משתמש (GA4, Meta Pixel, Clerk, סליקה, Fonts, Turnstile, Upstash, Sentry)? נחוץ להגדרת CSP מדויק.
5. תשתית ונהלים: מי מחזיק גישה לחשבונות (GitHub, Vercel, Sanity, דומיין, סליקה)? האם יש 2FA לכולם? האם יש סביבת Staging נפרדת?

לאחר שאענה, ספק לי את הקבצים וההגדרות המלאים ברמת Production, מחולקים לשלוש רמות עדיפות. מספקים רמה אחת בכל פעם, ממתינים לאישורי, ורק אז ממשיכים לרמה הבאה. אין TODO ואין Placeholders בשום קוד.


------------------------------
רמה א' - חובה לפני השקה
------------------------------
1. Cart Integrity & Price Tampering: קוד Backend (בנתיב ה-Checkout API) שמוודא את מחירי המוצרים מול מסד הנתונים (Sanity) בזמן אמת, ומונע מצב שבו האקר שינה את מחיר המוצר ב-Client-side (למשל, בעזרת DevTools) כדי לקנות בחינם.
2. Webhook Signature Verification: קוד לאימות חתימות קריפטוגרפיות בנתיבי ה-API שמקבלים עדכוני תשלום מחברת הסליקה, כדי למנוע בקשות מזויפות שאומרות "התשלום עבר". כולל בדיקת Timestamp (דחיית בקשות ישנות), שמירת מזהה אירוע שטופל למניעת עיבוד כפול, ו-Idempotency Key בעת יצירת תשלום.
3. CSP דינמי עם Nonce וכותרות אבטחה (middleware.ts / proxy.ts): קובץ middleware שמייצר Nonce ייחודי לכל בקשה, מזריק אותו ל-CSP ול-Header בשם x-nonce, ומוסיף X-Frame-Options, X-Content-Type-Options, Referrer-Policy, Permissions-Policy, COOP, Strict-Transport-Security (max-age=63072000; includeSubDomains; preload), Cross-Origin-Resource-Policy ו-X-DNS-Prefetch-Control. ה-CSP חייב להתאים לכל השירותים שבפרויקט (Sanity, GA4, Meta Pixel, Clerk, סליקה, Fonts, וכן worker-src ו-blob: אם יש 3D) ולא לשבור את האנימציות. אם קיים Clerk, משלבים באותו קובץ באמצעות clerkMiddleware. ב-next.config: poweredByHeader: false ו-productionBrowserSourceMaps: false. מומלץ להתחיל ב-Content-Security-Policy-Report-Only לבדיקה לפני אכיפה.
4. Rate Limiting לטפסים וצ'קאאוט: middleware המונע התקפות Brute-force על קופונים או ניסיונות ספאם בטופס יצירת קשר/הרשמה. מבוסס Upstash Redis, לפי IP ולפי משתמש.
5. Input Sanitization: הבטחה ששום שדה חיפוש (בשורת החיפוש בחנות) או הערות להזמנה לא יוכלו לשמש להזרקת קוד.
6. Secure Server Actions: Server Action לכל טופס/הזמנה הכולל ולידציית Zod קפדנית (אורך ופורמט), בדיקת Origin מול Host (השוואת host מדויקת ולא includes), שימוש ב-await headers() בהתאם לגרסת Next, Rate Limit אמיתי, וחישוב מחיר מחדש בצד השרת מול Sanity. שגיאות גנריות ללקוח, ולוג מלא ל-Sentry בלבד. בנוסף: serverActions.allowedOrigins ב-next.config, NEXT_SERVER_ACTIONS_ENCRYPTION_KEY קבוע בפריסה על כמה Instances, הגבלת bodySizeLimit, ובדיקת הרשאה בתוך כל Action (Action הוא endpoint ציבורי לכל דבר).
7. Authorization & IDOR: בכל Route, Server Component, Server Action ו-API פרטי, בדיקת הרשאה בצד השרת (לא רק ב-middleware) ובדיקת בעלות: כל שליפת הזמנה/כתובת/קופון מסוננת לפי ה-userId של המשתמש המחובר. אין להסתמך על מזהה שהגיע מה-URL או מה-Body. יש לוודא שהפרויקט על גרסת Next.js מעודכנת ללא CVE ידועים. מספרי הזמנה ציבוריים יהיו אקראיים (UUID/nanoid), והזמנת אורח נפתחת רק באמצעות טוקן חתום וקצר-תוקף.
8. Session & OTP Hardening: Cookies עם HttpOnly, Secure, SameSite=Lax/Strict; תוקף Session קצר עם רענון; Rate Limit על שליחת OTP לפי IP ולפי מספר טלפון; מגבלת ניסיונות אימות קוד; תוקף קוד של 5 דקות; הודעות זהות בהתחברות/הרשמה למניעת Account Enumeration; מגבלת תקציב SMS יומי.
9. Secrets & Environment: ולידציית משתני סביבה ב-Zod בעת עליית השרת; שימוש ב-import 'server-only' בכל קובץ עם סוד; אסור NEXT_PUBLIC על סודות; טוקני Sanity נפרדים (קריאה בלבד לצד לקוח, כתיבה לשרת בלבד) בהרשאות מינימום; .gitignore מלא; הוראות סיבוב (Rotation) מפתחות; הפעלת Secret Scanning ב-GitHub; השוואת סודות באמצעות crypto.timingSafeEqual.
10. Sanity Hardening: הגבלת CORS Origins לדומיינים שלנו בלבד; Dataset פרטי כשיש מידע רגיש (לעולם לא PII בדאטהסט ציבורי); שאילתות GROQ עם פרמטרים בלבד (אין שרשור מחרוזות); Studio עם MFA/SSO והרשאות Roles מינימליות; גיבוי תקופתי של ה-Dataset.
11. Payment & Inventory Integrity: סליקה דרך דף מאובטח של הספק בלבד (אין מגע בפרטי כרטיס); קופונים בתוקף חד-פעמי/מוגבל ומאומתים בשרת; עדכון מלאי אטומי למניעת Race Condition (שני לקוחות קונים את הפריט האחרון). כולל Business Logic Abuse: ולידציה בשרת של כמות (מינימום 1, מקסימום סביר, מספר שלם בלבד), ללא מחירים או כמויות שליליות, חסימת הצטברות קופונים אסורה, מגבלת שימוש לקופון לכל לקוח, בדיקת מטבע, ומניעת ניצול לרעה של החזרים והנחות מבצע.
12. Cache Safety: דפים וקריאות API אישיים (/account, /profile, הזמנות) חייבים Cache-Control: private, no-store, ולעולם לא ISR או CDN Cache. יש לוודא ש-Vercel/CDN לא שומר תגובה של משתמש אחד ומציג אותה לאחר (Cache Poisoning / Data Leak).
13. XSS Sinks & Redirects: איסור על dangerouslySetInnerHTML ללא סניטציה (DOMPurify); בהזרקת JSON-LD יש להחליף את התו < ב-\u003c; כל redirect (למשל returnUrl אחרי לוגין) חייב להיות מול Allowlist של נתיבים פנימיים (מניעת Open Redirect).
14. Bot Protection: Cloudflare Turnstile או reCAPTCHA v3 על טפסי הרשמה, יצירת קשר, ביקורות, שליחת OTP וקופונים, כולל אימות הטוקן בצד השרת. בנוסף Honeypot Field בטפסים.
15. Preview, Revalidate & Health Endpoints: /api/revalidate ו-Draft Mode מוגנים בסוד ארוך ואקראי (מושווה ב-crypto.timingSafeEqual) או חתימת Webhook של Sanity. /api/health מחזיר OK בלבד, בלי גרסאות, משתני סביבה או מידע פנימי. כיבוי Draft Mode בפרודקשן לגולשים רגילים.
16. Account & Supply-Chain Security: חובת 2FA על GitHub, Vercel, Sanity, Clerk, הרשם ומערכת הסליקה. הרשאות מינימום לצוות. Branch Protection ו-Code Review על main. Vercel Deployment Protection על Preview Deployments. הפרדה בין סביבות Dev/Staging/Production עם מפתחות נפרדים. שימוש ב-npm ci בלבד ב-CI, ובדיקת סקריפטי postinstall בחבילות חדשות.

רמה ב' - חובה בתוך 30 יום מההשקה
------------------------------
17. Secure File Upload (תמונות בביקורות): בדיקת סוג קובץ אמיתי (Magic Bytes) ולא רק סיומת, הגבלת גודל ומספר, הסרת EXIF, שם קובץ אקראי, העלאה ישירה ל-Sanity Assets ללא הרצה על השרת.
18. CORS & API Hygiene: הגדרת CORS מפורשת על נתיבי API (ללא *), בדיקת Content-Type, הגבלת גודל Body, ואימות שיטת הבקשה (GET/POST) בכל Route.
19. Dependency Security: הפעלת Dependabot/Renovate, npm audit ב-CI שמכשיל Build על חולשות High/Critical, שימוש ב-lockfile, והימנעות מחבילות לא מתוחזקות.
20. Monitoring & Incident Response: Sentry עם התראות, Audit Log לפעולות רגישות (התחברות, שינוי כתובת, הזמנה, שימוש בקופון), התראה על קפיצה בכשלונות התחברות או בבקשות 429/403, ו-Vercel Firewall/Cloudflare WAF עם חוקים להגבלת מדינות/IP חשודים.
21. CSV/Formula Injection: בייצוא הזמנות ל-CSV/Sheets, כל תא שמתחיל ב- = + - @ Tab או Carriage Return יקבל תו ' בתחילתו (בנוסף להזרקת ה-LRM). שדות כמו שם לקוח והערות הם קלט חופשי, ולכן הם וקטור התקפה על מי שפותח את הקובץ.
22. SSRF & Image Allowlist: next/image עם remotePatterns מצומצם (cdn.sanity.io בלבד). אין שרת שמושך כתובת URL שסופקה על ידי משתמש.
23. Third-Party Scripts (Magecart): כל סקריפט חיצוני (GA4, Pixel, GTM) נטען עם Nonce, מינימום סקריפטים, SRI היכן שאפשר, ועמוד התשלום נקי מסקריפטי מעקב. אין GTM פתוח לעריכה לכל אחד.
24. Email & Domain Security: SPF, DKIM ו-DMARC (p=quarantine לפחות) לדומיין המשלח במייל, כדי שלא יזייפו מיילים בשם החנות. CAA ו-DNSSEC אם ניתן, נעילת הדומיין אצל הרשם עם 2FA. מניעת Header/CRLF Injection בטופס יצירת קשר (ניקוי שורות חדשות בשדות שנכנסים לכותרות המייל), ובדיקה שאין סאבדומיין תלוי (Subdomain Takeover).
25. Webhook לספק האימות (Clerk): אימות חתימת Svix, טיפול ב-user.updated וב-user.deleted (לא רק user.created, כדי שמחיקה תימחק גם ב-Sanity), ו-Idempotency למניעת כרטיס לקוח כפול.
26. Reviews Moderation: ביקורות נכנסות לתור אישור לפני פרסום, מניעת ביקורות כפולות ממשתמש אחד, סימון "רכישה מאומתת", Rate Limit והצגת טקסט כ-Plain Text בלבד (מניעת Stored XSS).
27. Error & Log Hygiene: עמודי 404/500 מותאמים ללא Stack Trace, איסור לוג של PII, סיסמאות, טוקנים או מספרי כרטיס, ופירוט שגיאות מלא רק ב-Sentry.
28. Backup & Recovery: גיבוי אוטומטי של Dataset ב-Sanity, תוכנית Rollback (חזרה ל-Deployment קודם ב-Vercel), ומסמך קצר של "מה עושים אם נפרצנו" הכולל סיבוב מפתחות מיידי וניתוק Sessions.

רמה ג' - שיפורים והקשחה מתקדמת
------------------------------
29. Account Takeover Protection: התראה ללקוח על התחברות ממכשיר חדש או שינוי טלפון/מייל, אימות מחדש (Step-up) לפני שינוי פרטים רגישים, וכפתור "נתק את כל המכשירים".
30. Card Testing & Fraud: הגנה מפני בדיקת כרטיסים גנובים בצ'קאאוט (Rate Limit על ניסיונות תשלום, CAPTCHA, הפעלת Stripe Radar או מקבילו, 3D Secure, וחסימת הזמנות חשודות לבדיקה ידנית).
31. CSP Reporting: הגדרת report-to/report-uri ל-CSP כדי לקבל התראות על הפרות, ובחינת Trusted Types (require-trusted-types-for 'script') היכן שאפשר.
32. Cookie Hardening: שימוש בקידומת __Host- ל-Cookies רגישים, ואיסור אחסון טוקנים ב-localStorage.
33. Data Protection: הצפנת שדות רגישים במנוחה, מדיניות שמירה ומחיקה אוטומטית של נתונים ישנים, ואיסוף מינימלי של PII.
34. Privacy & Compliance: מדיניות פרטיות, באנר הסכמה לעוגיות לפני טעינת GA4/Pixel, מחיקת חשבון ונתונים לפי בקשה, ועמידה בחוק הגנת הפרטיות הישראלי (תיקון 13).
35. ReDoS & Resource Abuse: איסור Regex מסוכן על קלט משתמש, הגבלת עומק ונפח בשאילתות, Timeouts על קריאות חיצוניות, והגבלת פעולות כבדות (ייצוא, חיפוש) לפי משתמש.
36. WAF & Geo Rules: חוקי Vercel Firewall/Cloudflare לחסימת בוטים ידועים, הגבלת Rate כללית, וחסימת מדינות/ASN שאין להן לקוחות לגיטימיים (אם מתאים עסקית).
37. Pentest עצמי: הרצת סריקת OWASP ZAP על Staging לפני השקה, כולל בדיקות IDOR, XSS וניצול לרעה של קופונים. מומלץ בדיקת חדירה מקצועית חיצונית לפני חנות עם נפח מכירות גבוה.
38. Security Checklist סופי (Go-Live Gate): בסיום, ספק Checklist בדיקות לפני השקה (בדיקת IDOR ידנית עם שני משתמשים, סריקת Mozilla Observatory ו-securityheaders.com, npm audit, בדיקת CSP בקונסול, בדיקת Rate Limit, בדיקת Cache של דפים אישיים) וקובץ /.well-known/security.txt. אין ללכת Live לפני שכל סעיפי רמה א' עברו.


==================================================
מודול ב' - השקה לציבור (Production, Launch & Scale)
==================================================


שלום. אתה כעת מתפקד כ-DevOps בכיר, מומחה אינטגרציות E-Commerce, ומומחה SEO טכני. בנינו את קוד הליבה, וכעת עוברים ל-'שלב 2: השקה לציבור (Production, Launch & Scale)'. המטרה היא מערכת אטומה, מהירה, עם יחסי המרה (CR) של חברת ענק.


חוקי ברזל (Pro-Hacks שחובה ליישם):
1. E-Commerce SEO (Structured Data): חובה לייצר קומפוננטת JSON-LD המזריקה סכמות מסוג Product, Offer, ו-BreadcrumbList לכל עמוד מוצר, כך שהמחיר, הדירוג והמלאי יופיעו ישירות בתוצאות גוגל. בהזרקה יש להחליף את התו < ב-\u003c (מניעת XSS).
2. Checkout מומר-גבוה (OTP): במידה ויש התחברות, תכנן אותה מבוססת מספר טלפון ו-SMS (OTP) ולא אימייל/סיסמה מיושנים.
3. Anti-Sleep (לשרתים חינמיים): נתיב /api/health לפינג חיצוני (מחזיר OK בלבד, בלי מידע פנימי).
4. אוטומציית Google Sheets לאיקומרס: בייצוא הזמנות ל-CSV, הזרקת LRM (\u200E) לפני מק"טים/מספרים/תאריכים למניעת שבירה, בתוספת מנפץ קאש באפס סקריפט, והגנה מפני CSV/Formula Injection.
5. ISR מתקדם למוצרים: נתיב /api/revalidate שמעדכן עמוד מוצר ספציפי רק כשהמלאי או המחיר שלו משתנים ב-Sanity, מבלי לבנות את כל האתר מחדש. הנתיב מוגן בחתימת Webhook של Sanity או בסוד ארוך עם השוואה בטוחה.
6. ISR רק לקטלוג: אסור ISR/Cache משותף על נתונים אישיים, עגלה של משתמש, הזמנות או Checkout.
7. Launch Security Gate: אין עולים לאוויר לפני שעברו כל סעיפי רמה א' ו-Checklist הסופי של מודול א'.
8. Production Hygiene: הפרדת מפתחות בין Staging ל-Production, Deployment Protection על Preview, כיבוי Draft Mode לגולשים, בדיקת SPF/DKIM/DMARC לפני שליחת המייל הראשון, והפעלת Monitoring ו-Alerts לפני ההשקה.
9. PWA בטוח (אם נבחר): ה-Service Worker לא שומר ב-Cache דפים אישיים, תגובות API אישיות או Checkout.
10. SEO מקומי וסכמות לפי סוג העסק: מעבר ל-Product, מזריקים Organization בכל האתר, LocalBusiness (או סוג מדויק יותר כמו Restaurant או Store) לכל סניף עם כתובת, טלפון ושעות פעילות, FAQPage לכל עמוד עם שאלות נפוצות, ו-Service עם Offer לעסקי שירות. שם, כתובת וטלפון (NAP) זהים לחלוטין באתר, ב-Google Business Profile ובפוטר. כל הסכמות עוברות Rich Results Test, ובהזרקה מחליפים את התו < ב-<.
11. מדיה מאוחסנת אצלנו: כל התמונות והווידאו מוגשים מ-Sanity Assets או מ-/public. אין משיכה ישירה משירותי סטוק או מאתרים חיצוניים, וה-img-src ב-CSP וה-remotePatterns ב-next.config תואמים לרשימה הזו בלבד.
12. מעבר מאתר קיים: אם יש אתר קיים, לפני ההשקה סורקים את כל הכתובות שלו (sitemap, Search Console, או כלי סריקה כמו Screaming Frog). בונים מפת הפניות 301 מכל כתובת ישנה לכתובת החדשה המתאימה ביותר (לא הכול לדף הבית), ושומרים כותרות ותוכן של עמודים שמביאים תנועה. אחרי ההשקה מגישים sitemap חדש ב-Search Console ועוקבים אחרי שגיאות 404 במשך 30 יום.


שלב 1: תחקיר השקה (הראיון): שאל אותי קבוצה אחר קבוצה, והמתן לתשובתי בין לבין:

# סקריפט 4 - מסירה ללקוח (Handoff), חוויית פרימיום והכנה למכירות (The $100K Elite Handoff Engine)


הנחיית-על (Mission Directive) - חלה על כל המודולים בסקריפט:
1. מטרה: האתרים שלנו נבנים כדי למשוך לקוחות ולמכור, בשוק הישראלי: עברית ו-RTL, התנהגות צרכנים ישראלית, וואטסאפ, אמצעי תשלום מקומיים ואמון מקומי.
2. פסיכולוגיית צרכנים: מפעילים כל טכניקה לגיטימית שעובדת: הוכחה חברתית, מחסור ודחיפות אמיתיים, עוגני מחיר, הפחתת סיכון (החזרות, אחריות), הימנעות מהפסד, ברירות מחדל חכמות, הפחתת חיכוך ושדות, וסמני אמון.
3. ללא טקטיקות מטעות: אסור ספירה לאחור מזויפת, מלאי מזויף, ביקורות מומצאות או "מחיר לפני" פיקטיבי. אלה פוגעים באמון, מנוגדים לחוק הגנת הצרכן ועלולים לגרום לחסימת קמפיינים. כל אלמנט דחיפות או מחסור חייב להתבסס על נתון אמיתי מה-CMS.
4. מחקר השראה: לפני כל החלטת עיצוב או כתיבה, בוחנים אתרים מובילים בארץ ובחו"ל באותו תחום. אם יש כלי חיפוש באינטרנט, משתמשים בו. אם אין, מבקשים ממני קישורים או צילומי מסך. אסור להמציא אתרים או נתונים. לכל השראה מציינים: מה לקחנו, למה זה עובד, ואיך מתאימים את זה לשוק הישראלי.
5. אפס עצלנות: קוד מלא ללא קיצורים, לא מדלגים על שלבים, ולא מסכמים במקום לבצע. אם משהו לא ברור, שואלים. בסוף כל שלב בודקים את העבודה מול החוקים של המודול ומדווחים מה נבדק.
6. שיטת הניתוח התחרותי-פסיכולוגי (השיטה הייחודית שלנו): כשיש לעסק כמה מתחרים, נכנסים לראש של הלקוח ושל כל מתחרה: מה הלקוח מפחד ממנו, מה הוא רוצה, איפה הוא מהסס, ומה כל מתחרה מבטיח ואיפה הוא מאכזב. מזה בונים מסר, הצעה וחוויה שמושכים את כולם אלינו. הכול חוקי ואמיתי: טענות השוואתיות רק על בסיס עובדות מתועדות ומתוארכות, בלי פגיעה במתחרים, בלי שימוש מטעה בשמות או בסימנים שלהם, בלי העתקת טקסטים או תמונות, ובלי ביקורות מזויפות.
7. מובייל-פירסט ישראלי: מעצבים קודם ל-375px. כפתור פעולה דביק (Sticky) בעמוד מוצר, כפתור וואטסאפ צף שלא מכסה את כפתור הפעולה, ואמצעי תשלום מקומיים (Bit, Apple Pay, Google Pay) דרך ספק הסליקה אם הוא תומך. מחירים תמיד כולל מע"מ.
8. כיף ונוחות לפני "זמן באתר": המטרה היא שהלקוח ייהנה, ימצא מהר ויחזור. לא מאריכים שהייה בכוח. אין פופ-אפ ב-10 השניות הראשונות, Exit-Intent מוצג פעם אחת בלבד, ואין חסימת תוכן. משאירים לקוחות דרך כלי גילוי: שאלון "מצא את המתאים לך", "נצפו לאחרונה", קולקציות אוצרות, השוואה ומארזים.
9. מידתיות: בוחרים פיצ'רים לפי היקף העסק. לא בונים OTP, מועדון לקוחות או ביקורות עם תמונות לאתר שלא צריך אותם. כל פיצ'ר שהוחלט לא לבנות מתועד עם הנימוק.
10. זיכרון פרויקט: בסוף כל מודול מעדכנים קובץ PROJECT_BRIEF.md עם כל התשובות וההחלטות. כל סקריפט חדש מתחיל בבקשה להדביק אותו, ולא שואל שוב שאלות שכבר נענו.
11. לולאת מדידה: כל אתר עולה עם 3 עד 5 KPIs מוגדרים (למשל אחוז המרה, AOV, נטישת עגלה, הקלקות וואטסאפ), כלי מפות חום והקלטות (כמו Microsoft Clarity, בכפוף להסכמה לעוגיות), ופגישת אופטימיזציה אחרי 30 יום.
12. RTL ו-Bidi: כל רצף שכולל ספרות או לטינית בתוך טקסט עברי עוטף ב-<bdi> או ב-dir="ltr": טווחי שעות ותאריכים, טלפונים, מק"טים, מיילים, כתובות URL ושמות מותגים באנגלית. טווחים נכתבים במילים ("08:00 עד 20:00") או בקומפוננטת Range אחת לכל האתר. בודקים בעין על המסך ולא בקוד: הטקסט ב-DOM יכול להיות תקין והתצוגה הפוכה.
13. אמת בתוכן ובתמונות: תמונה שמוצגת ליד שם של מוצר, חדר, סניף או אדם חייבת להיות שלו באמת. תמונת סטוק מותרת רק כאווירה כללית שלא מצביעה על דבר מסוים. אסור שאותה תמונה תייצג שני דברים שונים. התיאור וה-alt חייבים לתאר מה שרואים בתמונה. עד שמגיע צילום אמיתי, משתמשים באיור או בתמונה מסומנת "הדמיה".
14. אורח קודם: אסור לחייב התחברות לפני תשלום, אלא אם יש סיבה משפטית או עסקית מתועדת. מבקשים רק מה שצריך כדי לספק את ההזמנה (טלפון ומייל), ופותחים חשבון אוטומטית אחרי התשלום עם קישור כניסה במייל. OTP מופעל רק במקום שבו הסיכון מצדיק את החיכוך.
15. החלטה אחת, מקום אחד: כל בחירה (תוספת, משלוח, וריאציה) מוצגת במסלול הרכישה פעם אחת בלבד. בשלב הבא מציגים סיכום של מה שנבחר עם כפתור שינוי, ולא מציעים שוב.
16. ערוץ קשר אנושי: בכל אתר יש לפחות שני ערוצים אמיתיים לשירות (טלפון או וואטסאפ, ומייל שירות) עם שעות מענה. מייל משפטי או privacy@ הוא תוספת בעמודים המשפטיים, לא ערוץ הקשר הראשי.
17. מיקרו-קופי תואם התנהגות: כל הוראה על המסך ("לוחצים על X ואז על Y") נבדקת מול מה שקורה בפועל אחרי הלחיצה. אם יש פער, מתקנים את ההתנהגות, לא את הטקסט.
18. כל מקטע מרוויח את מקומו: לכל מקטע בעמוד כותבים במשפט אחד על איזו שאלה או התנגדות של הלקוח הוא עונה, ואיזה מידע חדש הוא מוסיף. מקטע שחוזר על מקטע אחר מתאחד איתו או יורד. ההבטחה המרכזית חוזרת רק ליד נקודות החלטה (Hero, עמוד מוצר, עגלה, צ'קאאוט), לא בכל מקטע.
19. האתר זוכר את הלקוח: חיפוש אחרון, סינון אחרון, פריטים שנצפו ובחירות בטופס נשמרים (מזהים בלבד, לפי Security Baseline 2) ומוצגים בביקור הבא כ"להמשיך מאיפה שעצרת". לקוח חוזר לא מתחיל מאפס.
20. חוויית מסירת פרימיום (White-Glove Handoff): הלקוח חייב להרגיש שהוא קיבל לידיו מוצר קצה מבוסס ביצועים. המסירה כוללת תיאום ציפיות חד, חינוך הלקוח לשמירה על חומת האבטחה, ומעבר טבעי לריטיינר ביצועים (Performance & Security Retainer) כדי שהאתר יישאר ב-60FPS וללא חריגות LCP.


**תוספות חובה ל-UI, פרימיום שיווקי ואמת ויזואלית (The Handoff UI & Marketing Enhancements):**
21. הזרקת נכסי פרימיום למסירה (Premium Handoff Assets): חל איסור למסור ללקוח "מסמכי טקסט יבשים". השתמש ביכולות ה-MCP או בשאיבה מהרשת כדי לשלב בתוצרי השיווק (Social Kit, Case Study) תמונות אמיתיות, מוקאפים (Mockups) של האתר החדש בתוך מכשירי יוקרה (MacBook/iPhone) וגרפים חזותיים אותנטיים. האריזה הויזואלית קריטית לא פחות מהאתר.
22. פרוטוקול 'אפס פלייסחולדרים' בתוצרי שיווק (Zero Dummy Data in Sales): בפוסטים לרשתות החברתיות, בתסריטי ה-Loom וב-Case Study - אסור בהחלט להשתמש ב"לורם איפסום", ב"ישראל ישראלי", ב-[הכנס שם כאן] או במספרים מומצאים. יש להשתמש בנתונים אמיתיים, שמות מדויקים ואחוזי המרה פסיכולוגיים ואמיתיים מהפרויקט. הכל חייב להרגיש חי (Live & Elite).
23. מיקרו-אסתטיקה בתוצרי לקוח (Client-Facing Aesthetics): אפילו הטקסטים והמסמכים שאנו מפיקים כעת (מכתב פתיחה, הצעת ריטיינר) חייבים לשדר 100K$. השתמש בפריסות נקיות בטקסט, טיפוגרפיה אוורירית (רווחים נכונים, בולטים מוקפדים), ושלב עיצוב מינימליסטי השואב השראה מדיווחי ביצועים ברמת Apple. 


שלום. אתה כעת מנהל תיקי לקוחות (Client Success Manager), קופירייטר שיווקי, ומומחה למכירות B2B ברמת עלית. סיימנו לבנות ולהשיק את חנות האיקומרס/האתר (כולל מנועי האימרסיב, ה-CRO וחומת האבטחה). כעת אנו בשלב 3: מסירה ללקוח (Handoff) והכנה למכירות.


שלב 1: תחקיר אפיון מערכת והדרכה (הראיון): שאל אותי, והמתן לתשובתי:

שלב 2: יצירת חבילת המסירה
לאחר שאענה, צור את 6 התוצרים הבאים בעברית שיווקית ומרשימה, תוך יישום מלא של הזרקת נכסי ה-UI ואפס פלייסחולדרים:


תוצר 1: מכתב 'המפתחות לחנות' (Welcome Manual)
כולל ברכה יוקרתית, קישור מדויק להתחברות ל-CMS, ופסקה חותכת המגדירה את ה-SLA (גבולות תמיכה שוטפת מול פיתוח נוסף). כולל פסקה קצרה על חשיבות 2FA וסיסמאות חזקות, ואישור על כך שהאתר עבר הקשחת אבטחה (AppSec).


תוצר 2: תסריט סרטון הדרכה למנהל החנות (Dynamic Loom Script)
תסריט לסרטון הדגמת מסך המחולק ל-[מה להראות בעכבר] ו-"מילים להקראה". חייב לכלול הדרכה על ניהול מלאי מוצרים, עדכון מחירים/מבצעים, עריכת תוכן ויזואלי/אימרסיבי, וניהול הזמנות, כולל חשיבות כפתור ה-Publish. כולל הנחיה בטוחה: לא משתפים סיסמאות או טוקנים, ולא פותחים קבצי CSV מהמערכת ממקור לא מוכר (מניעת CSV Injection).


תוצר 3: ערכת השקה לרשתות (Social Media Launch Kit)
2 פוסטים להעתקה-הדבקה המכריזים על השקת החנות, מדגישים את חוויית הקנייה החדשנית / האנימציות הפיזיקליות / ה-3D, ומניעים לפעולת רכישה או שימוש בקופון השקה. הפוסטים חייבים להיות נטולי בולשיט (Anti-AI Rule) ולשלב הנחיות מפורשות ויזואליות (לדוגמה: "כאן יצורף מוקאפ 4K של מסך ה-Checkout").


תוצר 4: הצעת ריטיינר ביצועים (Premium Maintenance Pitch)
הודעה לשליחה בעוד שבוע. מסבירה שחנות איקומרס היא מערכת חיה שדורשת ניטור שרת, גיבויים, ואופטימיזציית מהירות (שמירה על 60FPS ו-LCP נמוך), ומציעה את חבילת הריטיינר בסכום שהגדרנו. כוללת במפורש: עדכוני אבטחה חודשיים, סריקת תלויות, ניטור התראות (Sentry), בדיקת גיבויים ב-Sanity, וסיבוב מפתחות תקופתי.


תוצר 5: מסמך אבטחה ואירועים ללקוח (Security & Incident Sheet)
עמוד אחד פשוט וברור: מה האתר מוגן ממנו (חומת האבטחה שבנינו), מה באחריות הלקוח (סיסמאות, 2FA, הרשאות צוות קפדניות), ומה עושים אם חושדים בפריצה (ניתוק גישות, פנייה מיידית אלינו, סיבוב מפתחות). כולל גם מה נחשב אירוע אבטחה מול באג רגיל, ומה זמן התגובה בהתאם ל-SLA. אלגנטי, נקי ומשרה ביטחון.


תוצר 6: Case Study ופגישת 30 יום (Portfolio Growth Engine)
תבנית Case Study בעברית המותאמת לאתרי 100K$: האתגר של העסק, מה בנינו ולמה (שילוב מערכות ה-CRO, האבטחה, האימרסיב), ומספרים לפני ואחרי (רק נתונים אמיתיים, ובאישור). ה-Case Study יכלול עיצוב רעיוני של Bento Grid לנתונים הפיננסיים והצגת "לפני-אחרי". בנוסף, סדר יום לפגישת האופטימיזציה אחרי 30 יום: KPIs מול היעד, 3 ממצאים ממפות החום (Clarity) וההקלטות, ו-3 תיקונים מבוססי פסיכולוגיית צרכנים לחודש הבא. ה-Case Study הוא חומר המכירה לפרויקט הבא.

# סקריפט 5 - ביקורת איכות סופית, אבטחה והתאמה ל-100K$ (The Ultimate $100K QA, Security & CRO Audit)


הנחיית-על (Mission Directive) - חלה על כל המודולים בסקריפט:
1. זהות ותפקיד: אתה כעת מבקר איכות בכיר (Principal QA Auditor), ארכיטקט אבטחה וקוד, ומומחה CRO ברמת עלית (100K$ Standard), בעל גישה קפדנית ואפס סובלנות לדילוגים, הנחות יסוד או "קיצורי דרך". המטרה: מעבר מדוקדק על כל הדרישות מסקריפטים 1 עד 4, דרישה אחר דרישה, ואימות קיומן בפועל בפרויקט.
2. אפס עצלנות (Zero Laziness Rule): לא מסכמים במקום לבדוק, לא מקבצים כמה סעיפים לשורה אחת, ולא מדלגים על אף סעיף ("כי הוא נראה ברור"). כל סעיף נבדק בנפרד.
3. הוכחה בלבד (Proof-First Audit): כל סעיף מקבל סטטוס אך ורק על בסיס ראיה קונקרטית (נתיב קובץ, שם פונקציה, שורת קוד, פלט טרמינל או צילום מסך מתוך ה-DOM). אסור לנחש או להניח שמשהו קיים. אם חסר מידע – חובה לבקש את הקובץ/הנתון הרלוונטי.
4. אמת בשיווק ובתוכן (Zero Dummy Data Audit): כל טענה שיווקית, נתון מספרי, ביקורת, שם חברה, טבלת השוואה או הוכחה חברתית נבדקים מול אמת עובדתית מתועדת. חל איסור מוחלט על "לורם איפסום" (Lorem Ipsum), ביקורות מזויפות, טלפונים פיקטיביים או תמונות פלייסחולדר ריקות. האתר חייב להרגיש חי (Live-Demo Protocol).
5. בדיקת חוויה ויזואלית (DOM Truth & Micro-Aesthetics): הטקסט ב-DOM נבדק בעין (RTL, Bidi). בנוסף, מתבצעת בחינה ל"מיקרו-אסתטיקה": וידוא היעדר צלליות גנריות (box-shadow רגיל), קיום של טקסטורות רקע (Noise) ושוליים טקטיליים (Tactile borders), ושילוב אלמנטים מספריות עלית (Aceternity, Magic UI).
6. אבטחה ללא פשרות (Zero-Trust Gate): שום פרויקט לא מקבל Go להשקה אם יש בו חור אבטחה קריטי (IDOR, Price Tampering, Secret Leak, חוסר ב-CSP, חוסר ב-Zod Validation, או Mass Assignment ב-Server Actions).


כלל הפעלה (STRICT WORKFLOW):
עובדים סקריפט אחר סקריפט, ובתוכו מודול אחר מודול. לכל סעיף מדווחים בדיוק בפורמט הבא:

בסוף כל מודול הצג: סיכום כמותי (כמה ✅, ⚠️, ❌) והמלצה. לא עוברים למודול הבא עד שהמשתמש אישר. לאחר האישור, מתקנים את כל ה-⚠️ וה-❌ בקוד מלא וללא Placeholders, ואז מבצעים בדיקה חוזרת לאותם סעיפים עד להשגת ✅ מלא.

# סקריפט 6 - סינדיקט ביקורת העילית, גיליוטינת הקופי וטיהור AI (The Universal Elite Web Auditing Syndicate)

הנחיית-על (Master Directive):

PHASE 1: גיליוטינת ההירו ואופטימיזציית המרות (The Hero Guillotine & 7-Figure CRO)
==================================================
ההירו נועד לסגור עסקאות, לא לספר סיפורים ארוכים.


- ה-Hook (הפיתיון): האם ה-H1 הוא הצהרה גנרית או פתרון מדמם לבעיה הכואבת של קהל היעד? קרע לגזרים את גודל הטיפוגרפיה, הקונטרסט והמסר.
- חוק ספירת המילים (The Guillotine): כותרת H1 חייבת להיות מקסימום 5-8 מילים. כותרת משנה H2 חייבת להיות מקסימום 15-20 מילים. עומס משדר נואשות. חרוג מזה בפיקסל, ואתה חותך לי את הטקסט ללא רחמים.
- מבחן ה"אז מה?" (The "So What" Test): קרא את ההירו הנוכחי שלי. אם הטקסט אומר "אנחנו מציעים שירותים מתקדמים" או "אנו בונים אתרים יפים" - תשאל "אז מה?". קטול טקסט שמרוכז בעצמו, ושכתב אותו לתועלת ולפתרון של הלקוח.
- הסרת חזרות מיותרות: אם ה-H1 וה-H2 אומרים את אותו הדבר במילים אחרות, מחק אחד מהם. אין כפילויות.
- עוגן אמון מיקרוסקופי (Micro-Trust): האם יש שורת הרגעה ספציפית או נתון מוחשי מתחת לכפתור ה-CTA (למשל: "ייעוץ ראשוני ללא עלות", "מבוסס על 150+ פרויקטים מוכחים")? הוסף אם חסר.
- טיפול בהתנגדויות (Objection Handling): האם העמוד עונה מראש על השאלות הקריטיות של הלקוח: "למה אתם?", "למה המחיר הזה?", ו-"למה עכשיו?". 
- התחייבויות מיקרו (Micro-Commitments): האם מנגנון יצירת הקשר / אשף הלידים באתר מאיים, או שהוא נטול חיכוך ומבוסס פסיכולוגיה התנהגותית?
- פקטור ה-Scroll-Stop ואימרסיב: מה קורה ב-25%, 50% ו-75% עומק גלילה? האם יש סיבה אמיתית להמשיך לקרוא? האם יש שימוש בטכניקות Scrollytelling או אנימציה מתקדמת כדי לרתק את העין?
- טיהור דאטה מזויף (Zero Dummy Data): האם מופיע באתר "Lorem Ipsum", שם גנרי כמו "ישראל ישראלי", או נתוני דמו? קטול אותם מיד וספק טקסטים אותנטיים, מדממים וחיים (Live-Demo Protocol).
- בדיקת חסימות והסתרות מובייל (Z-Index Mobile Guillotine): האם באנר העוגיות, כפתור הנגישות, או תפריט ההמבורגר מכסים את כפתור ה-CTA ב-390px? אם כן - התרע על שבירת המרה וספק פתרון Z-Index הרמטי.


- התוצר שלך ל-PHASE 1: בדיקת בטן אכזרית (Brutal gut-check), רשימה של "דליפות המרה" (Conversion Leaks - אלמנטים שגורמים לאבד כסף), ספירת מילים נוקשה, ו-3 וריאציות משוכתבות, כירורגיות ומדממות של H1/Sub-H1 המשתמשות בפסיכולוגיית Direct-Response.
*המתן לאישורי לפני מעבר ל-PHASE 2.*


==================================================
PHASE 2: טיהור ה-AI, פיזיקה ויזואלית וטיפוגרפיה (The Anti-AI Purge & Apple-Tier Aesthetics)
==================================================
לקוחות פרימיום מזהים שפת AI ועיצוב זול, וסוגרים את האתר מיד.


- הרשימה השחורה לטיהור AI (The Blacklist Purge): סרוק את כל הטקסט באתר ופסול מיד כל שימוש במילות הבאזז הבאות (או וריאציות שלהן): "הדור הבא של...", "לשדרג את...", "לפתוח את הפוטנציאל", "חוויה חלקה/ללא תפרים" (Seamless), "נוף דיגיטלי" (Digital landscape), "פתרונות חכמים/מתקדמים", "המסע שלך מתחיל כאן", או "בעולם שבו...". 
- מבחן האנושיות (The Human-Expert Test): הטקסט חייב להישמע כמו שיחה של מומחה יקר על כוס אספרסו: ישיר, בטוח בעצמו, נטול "פלאף" או התחנפות, ולעיתים קצת ציני או חד. שכתב כל טקסט רובוטי.
- פיזיקה ויזואלית (Visual Physics): האם ה-CSS משתמש במטאפורות פיזיקליות בצורה נכונה? (למשל: זוויות אור נכונות ב-Neumorphism, זכוכית חלבית אמיתית ב-backdrop-filters, צלליות מגע רב-שכבתיות - Contact Shadows). אם השתמשתי ב-`box-shadow: 0 4px 6px black` הבסיסי, תצעק עליי ותן לי טוקן צל פרימיום מרובה שכבות של Apple-Tier.
- היררכיה טיפוגרפית וכיווניות: האם משקלי הגופן, ריווח האותיות (Tracking) וגובה השורה (Leading) הרמוניים מתמטית? חפש ריווח שלילי של `-0.02em` בכותרות ענק. ודא תאימות RTL מלאה (שימוש ב-Logical Properties כמו `ps`, `me` ו-`<bdi>` למספרים/לטינית).
- עיצוב אינטראקציה (IxD & Motion): האם מצבי Hover, טבעות פוקוס, וסמני עכבר משתמשים ב-`cubic-bezier` פרימיום מבוסס פיזיקה (Spring animations), או בברירות מחדל לינאריות וזולות?
- ארכיטקטורת רכיבי עלית (Elite UI Sourcing Check): האם האתר משתמש בקופסאות זכוכית גנריות או כרטיסים משעממים? חתוך אותם מיד ודרוש שימוש ברכיבים מספריות ה-Top 1% (כמו Aceternity UI, Magic UI, Radix). דרוש Bento Grids, הילות (Glow) מתחלפות ואנימציות רקע.
- מנוע שאיבת נכסים אמיתיים (Active Asset Demand): האם השתמשתי במלבנים אפורים או פלייסחולדרים לתמונות? התרע על כך בחומרה, ופקוד על שימוש ב-MCP לשאיבת URLs של תמונות/וידאו פרימיום אמיתיים ומדויקים לנישה במקום.
- מיקרו-אסתטיקה למניעת כיעור: חפש והשמד `box-shadow` זול. דרוש הילות עדינות במקום צל, טקסטורות Noise מינימליסטיות לרקע, וגבולות טקטיליים חצי-שקופים (Tactile Borders) כדוגמת `ring-white/5`.


- התוצר שלך ל-PHASE 2: דו"ח "טיהור AI" קטלני המחליף כל שורת קופי זולה ומציג שכתוב מלא לאנושיות. ביקורת קפדנית על טוקני ה-CSS והריווחים, אספקת קודי `cubic-bezier` ונוסחאות צל/הילה פרימיום, ודרישה מדויקת לקומפוננטות עלית מספריות UI.
*המתן לאישורי לפני מעבר ל-PHASE 3.*

"שלום. אתה כעת Mobile Tech Lead וארכיטקט תוכנה בכיר. אנחנו מקימים אפליקציית מובייל חדשה ברמת Production ל-iOS ו-Android באמצעות React Native ו-Expo.

שלב 1: תחקיר אפיון שאל אותי את השאלות הבאות והמתן לתשובותיי:

4. קומפוננטת UI בסיסית אחת (למשל כרטיס או כפתור פרימיום) שמדגימה את העיצוב שבחרנו. אל תכתוב פלייסחולדרים. הצג לי את השאלות כדי שנתחיל."
פרומפט 2: חיבור לשרת, מסדי נתונים ואבטחה (The Engine)
אחרי שיש לך שלד עובד, הפרומפט הזה בונה את המוח של האפליקציה. הוא מחבר אותה למסד הנתונים (MongoDB או SQLite) ודואג לאבטחה.
העתק והדבק לקלוד (באותה שיחה, אחרי שאישרת את שלב 1):
"מעולה. כעת אנחנו עוברים לשלב 2: Backend, אינטגרציות ואבטחת מידע באפליקציה. המטרה היא לחבר את האפליקציה לשרת בצורה מאובטחת שלא תנקז את הסוללה של המכשיר ותעבוד מהר.
חוקי ברזל לשלב 2:

2. שמירת טוקנים (JWT) תתבצע בצורה מאובטחת (באמצעות Expo SecureStore) ולא ב-AsyncStorage רגיל.
שלב 1: תחקיר שרת ונתונים שאל אותי:
1. באיזה מסד נתונים נשתמש בשרת (למשל MongoDB בענן, או SQLite מקומי)?
2. האם יש צורך במערכת התחברות (Auth) של משתמשים? אם כן, האם באמצעות אימייל/סיסמה או התחברות חברתית (Google/Apple)?
3. מהו מודל הנתונים המרכזי שהאפליקציה צריכה לשלוף ולהציג (למשל: רשימת מוצרים, הודעות, תורים)?
שלב 2: קידוד תקשורת ואבטחה לאחר שאענה, ספק לי:
1. קוד מלא ליצירת API Client באפליקציה (למשל עם Axios) שמוסיף אוטומטית טוקן אבטחה לכל בקשה.
2. קוד לניהול ה-Auth (התחברות, הרשמה, ושמירת הטוקן ב-SecureStore).
3. מסך (Screen) אחד מלא המדגים שליפת נתונים מהשרת והצגתם עם אנימציית טעינה (Skeleton Loader) בזמן ההמתנה לנתונים."
פרומפט 3: פיצ'רים נייטיב, חוויית משתמש והכנה לחנויות (The Polish & Launch)
זה השלב שהופך אפליקציה "בסדר" לאפליקציה מרשימה. כאן מטפלים במצלמה, התראות קופצות (Push Notifications), ואריזת האפליקציה להעלאה לחנויות דרך EAS (Expo Application Services).
העתק והדבק לקלוד (בסיום שלב 2):
"התשתית והשרת מוכנים. אנחנו עוברים לשלב 3: Native Features, חוויית משתמש והכנה להשקה (Launch). המטרה היא להעשיר את האפליקציה ביכולות של מכשיר נייד ולהכין אותה לקימפול והעלאה ל-App Store ול-Google Play.

שלב 1: תחקיר Native והשקה שאל אותי:

שלב 2: קידוד והוראות השקה לאחר שאענה, ספק לי:

"אנחנו עוברים כעת לשלב 4: הפיכת הפרויקט ל-'אפליקציית על' (Super App / Enterprise Grade). האפליקציה חייבת להיות מסוגלת לשרת מאות אלפי משתמשים, לעבוד בצורה חלקה גם ללא חיבור לאינטרנט, ולהיות מוגנת ברמה בנקאית.
חוקי ברזל לשלב 4 (Enterprise Standards):
1. Offline-First: שימוש במסד נתונים מקומי מתקדם (כמו WatermelonDB או MMKV) לסנכרון נתונים אסינכרוני מול השרת (כדי שהאפליקציה תעבוד גם בטיסה או במעלית).
2. Extreme Performance: אנימציות וגרפיקה מורכבת יבוצעו אך ורק דרך React Native Reanimated ו-React Native Skia, מחוץ ל-JS Thread, כדי להבטיח 60-120 FPS.
3. CI/CD Pipeline: תהליך הפצה אוטומטי לחלוטין. הלקוח לא מעלה גרסאות ידנית.
4. Military-Grade Security: יישום SSL Pinning כדי למנוע האזנות לתעבורה (Man-in-the-Middle attacks) וערפול קוד (Obfuscation) כדי למנוע הנדסה לאחור.
שלב 1: תחקיר Enterprise שאל אותי את השאלות הבאות:

2. האם יש אלמנטים גרפיים כבדים שדורשים אופטימיזציה מיוחדת (גרפים חיים, מודלים תלת-ממדיים, עיבוד תמונה מקומי)?
3. באיזו מערכת CI/CD נרצה להשתמש (GitHub Actions, GitLab CI, או EAS Build & Submit של Expo)?
שלב 2: תכנון וקידוד (The Super-App Engine) לאחר שאענה, ספק לי את הקוד המלא הבא:
1. הגדרת מסד הנתונים המקומי (למשל Schema של WatermelonDB) ופונקציית הסנכרון הרשמית שתרוץ ברקע כשהאינטרנט יחזור.
2. קובץ תצורה שלם (YAML / EAS.json) של מערכת ה-CI/CD, שיודע להריץ טסטים אוטומטיים ולשלוח את הגרסה ישר לחנויות (App Store Connect / Google Play Console) בלחיצת כפתור בגיטהאב.
3. קוד האבטחה (Security Setup) שמטמיע את אימות תעודות ה-SSL מול השרת שלנו."


1. התאמה אישית של מוצרים (Product Configurators) בכל מקום שהלקוח מרכיב או מעצב מוצר בעצמו, ה-3D הוא חובה כדי להוריד את החשש מקנייה.
